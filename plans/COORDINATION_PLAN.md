# Aide de camp — task and workspace coordination plan

Milestone 1 is implemented: workspace management, native attachable Codex sessions, monitoring/recovery, recordings, dashboard, and review launch integration. Milestone 2 remains open for experience with this version. The companion [review plan](REVIEW_PLAN.md) defines an independently usable tool.

**Naming:** Aide de camp in full, Aide for short, `aide` for the CLI. Keep `~/.aide` and project-local `.aide/` paths.

**Review commands — milestone 1:** rename the independent review executable to `aide-review`. `aide review` delegates to it for the current repository, without requiring a registered project or running dashboard. `aide task review <task-id>` resolves the task's workspace from project bookkeeping and launches the same review tool there; the dashboard's review action uses this operation. Preserve the review tool's arguments and normal start/resume behaviour. This integration only locates and launches the reviewer: it neither completes the task nor automatically submits feedback to its Codex conversation. All three command entry points are implemented.

**Repository:** the coordination workbench and review tool belong to the same Aide Cargo monorepo/workspace. They remain independently usable; exact crate boundaries and useful shared components will be established during implementation.

## Purpose and user

Minimize workspace housekeeping and time to regain context for a hands-on head of engineering who also contributes to open source. Work is frequently interrupted and shifts between coding, testing, and review. Slack and calls are outside scope.

Typically one main project has 10+ tasks; design for up to 10 projects and 30 tasks per project, with far fewer executing simultaneously. A project is a directory containing one or more related repository checkouts and private project files. **One task, one physical workspace; closing the task tears down that workspace.** Initially the user can launch an agent manually; managed harness sessions follow within milestone 1.

## Jobs and lifecycle

The full workflow below is the product direction; milestone 1 starts with direct workspace operations before first-officer/MCP integration.

Primary jobs: start and finish tasks with minimal setup/teardown, see ongoing work, and enter the relevant workspace or conversation quickly.

1. Start a task directly in the dashboard or plan it with the project supervisor; the first officer can route an initial request. The project supervisor draws on project history, personal context, and available tracker integrations. Conversational intake is not required for direct creation.
2. In milestone 1, select the project/repository and task ID, create a workspace from the latest trunk as resolved by jj, and open a fresh interactive Codex conversation in its terminal. The user plans and executes the task there; no initial brief or automatic implementation turn is required. Later, the project supervisor can supply a plan, launch the task or implementation loop, and bring it back for human review. During milestone 1, the user plays the project-supervisor role.
3. Develop through whatever planning, plan review, and implementation the task needs. Instructions define this evolving workflow.
4. Prepare local changes for the independent review tool; receive its text feedback and hand it to the task supervisor.
5. Iterate, then open a PR for owned work or approve a teammate’s PR after review.
6. The user explicitly finishes the task, either by telling the first officer or closing it in the UI. Both routes trigger the same cleanup workflow. Opening a PR or an agent finishing its work does not automatically close the task.

Alternate entry: check out someone else’s work into a dedicated workspace with an attached contextual agent, then enter review.

**CLI and browser:** task-management commands work from inside a project, including repository/task subdirectories, and discover the enclosing project root. Running `aide` with no arguments explicitly starts the local manager and browser dashboard covering all registered projects. **Manager lifecycle:** the dashboard manages and observes task runtimes, but does not own their lifetime. Closing a browser, task terminal, or Aide itself must leave task tmux sessions and Codex backends running. On dashboard startup, reconcile persisted runtime intent with reality: reconnect to surviving components and recover missing runtimes for previously running tasks, including after a machine reboot. Store intended runtime state separately from observed process status so deliberately stopped tasks remain stopped. Manage only Aide’s task sessions, never the shared tmux server or unrelated sessions.

**Shared visibility:** the user through the dashboard and the first officer through its tools have equivalent access to task status, workspace/session locations, and other dashboard information. Skills explain how the first officer discovers and inspects that information. Human and agent interfaces use the same underlying records and lifecycle operations.

Hierarchy: first officer → project supervisors → task supervisors → configurable role agents. This divides responsibilities; it does not require every request to traverse every level.

**First officer:** the usual entry point for new work. Clarifies intent, prepares briefs, and starts or delegates tasks. Coordinates overall staff, priorities, and execution shifts. Helps improve system efficiency by examining anomalies, suggesting improvements, and preparing briefings. The user remains the captain setting direction and judging outcomes.

**Project supervisor:** persists across tasks and maintains the user’s personal preferences, rules, and memory for that project. Plans tasks with the user using project context, active/completed task records, and tracker information; launches the implementation with the plan, supervises progress, and requests human review. Detailed implementation belongs to task agents. Personal context is distinct from shared project conventions, which focused agents must also respect. This is the future workflow; the user initially fills this role.

**Task supervisor:** exists only for the scope of one task. Receives the brief and project context, refines task details with the user as needed, and initially does the implementation work itself. The user works with it directly but intermittently; execution should not require continuous conversation. End its active role when the user closes the task rather than reusing it for unrelated work. Keep the completed task’s bookkeeping in the project database after workspace cleanup.

**Conversation lifecycle:** support suspending and resuming supervisor conversations with their existing context. Prefer controlling the harness’s lifecycle capabilities; the workbench maps sessions to roles/tasks and decides when work runs. Codex documents [resuming saved threads after process restart](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server). Conversation resumption and pausing in-flight tools/builds are separate concerns; validate execution behavior during technical design. Persistent project context does not require an always-running agent process.

**Durability:** accidental tmux/harness termination or a machine reboot must not end the task. Dashboard mode recovers missing tmux sessions and, where supported, resumes the stored native conversation in the existing workspace, both on startup and through a recovery action. Recovered conversations remain idle and tasks show requires attention with a recovery reason; do not submit another agent turn or replay interrupted commands automatically. Reconnecting to a surviving runtime leaves its ongoing work alone. `task attach` switches to an existing session directly; if it is missing, request recovery from the manager, or explain that dashboard mode must be started. Prevent duplicate runtimes. Explicitly completed tasks are not recreated.

**Session recording — milestone 1:** retain Codex’s native session recording format for later analysis; do not invent a separate transcript schema. Store the native session ID and references to retained recording artifacts under the global home in the project database. Preserve available conversation and tool/lifecycle history, not just terminal output or current status. Records must survive workspace cleanup and dashboard closure, including harness restarts. Validate native artifact capture/retention without disrupting the user’s Codex configuration or authentication. Retrospective analysis itself remains future work.

**Later extension:** give task supervisors their own staff: one implementer and two reviewers providing independent opinions. The supervisor coordinates implementation → independent reviews → consolidated feedback → revision until reviewers are satisfied. Different reviewer models are an experiment to evaluate in practice, not a requirement.

Supervisors retain the agreed intent and decisions, track unresolved issues, and present results for human review. Delegation and reviewer-feedback consolidation arrive with agent teams. Behavioral policies—autonomy, clarifications, escalation, and loop stopping—belong in editable skills and will be refined later. Automated reviewer acceptance means ready for human review.

## Resource coordination

Support many open workspaces with only one or two executing at once across projects. Whole-workspace turns are the proposed starting policy; limiting only expensive operations is an alternative. Keep browsing/review available while execution queues.

Turn boundaries, prioritization, and subagent/build limits remain open. Rust compilation also creates disk pressure: artifact reclamation needs its own policy, preserving source changes and task context.

## Automations and system improvement

Schedule instructions for checks, reports, or other work through the task/workspace model. Repeated-run behavior remains open.

Improving the global system is a job in its own right. Agent definitions and skills are authoritative plain files, editable directly or through conversation. Proposed distinction: definitions describe roles/delegation; skills describe workflows; memory retains context and lessons. Do not store these editable definitions in the operational database.

Candidate recurring task: a weekly retrospective analyzes recorded conversations and proposes skill/memory updates with supporting examples, supporting the first officer’s improvement role. Begin recording in milestone 1; memory scope and adoption of updates remain later decisions. Focused agents must respect repository instructions; prefer the harness’s existing support, to be verified later. Private project-supervisor context must also reach each task, including tasks started directly by the first officer.

### First implementation — agreed core scope, details below

Authentication through `gh`, N independent manually assigned PR links per task, distinct implementation/review responsibilities, and promotion of actionable tasks into Requires attention are agreed. Implementation PR tags summarize merge readiness: waiting for review (grey), ready to merge (green), or blocked by feedback/CI failure (yellow, needs attention). Track underlying CI and review facts separately for explanation. Branch/bookmark position never controls associations. Full PR URLs supply the initial host/repository context; local reference suggestions and revision comparisons remain optional follow-up work.

1. **Connection health:** reuse `gh` login for the explicit PR URL host and explain missing tooling/login/access inline. Full URLs identify the repository without remote mapping; discovery and mapping settings remain optional follow-up work.
2. **Task association:** explicitly link a PR by full URL (repository/number shorthand is deferred) and retain it while the workspace moves through commits or a stack. Branch/bookmark discovery may suggest a candidate but does not assign or replace it. Unlinked tasks are valid. Support N independent links, normally only a few, with add/remove and responsibility per link. No stack relationships or dependency ordering.
3. **Compact task-row status:** display one text-labelled tag per linked PR alongside task ID, terminal, and Codex tags. Each independently summarizes its role-specific status; implementation emphasizes merge readiness and review emphasizes re-requests/outcome. Any actionable linked PR puts the task in Requires attention, with reasons naming the PRs. Do not monitor CI or merge readiness for someone else's PR.
4. **Useful expanded details:** show the linked PR and responsibility, relevant check/review/request information, published head/base/SHA, and last refresh. Local branch/bookmark comparisons remain optional follow-up work. Moving to an older commit or another stack entry is expected and does not invalidate the link. Follow links to GitHub for full logs and review conversations.
5. **Refresh and recovery:** automatic shared polling plus manual refresh, clear stale/unavailable states, and restoration of associations after restart. A network/login failure cannot appear as successful CI or block task operations.
6. **Lifecycle and history:** show each PR's merged/closed state and retain links and last observations in completed task history. Task completion remains the user's explicit decision. Surface the same observations through CLI task inspection.

Deferrals: a GitHub inbox is explicitly separate future work. Publishing/pushing, PR creation or merging, CI reruns, replying to reviews, and notifications remain proposed deferrals. Do not model stacks, infer dependencies, order merges, or add an unread-comment/acknowledgment workflow. Multiple PRs are simply independent links.

### Authentication direction — GitHub CLI agreed, 2026-11-01

**Agreed direction:** use `gh` as an explicit, documented dependency for GitHub monitoring. This supersedes the earlier fine-grained PAT preference and direct credential-storage proposals. The user wants setup they can handle themselves without approval work for collaborators; normal auditing is acceptable. Manual renewal/reconnection is acceptable. Planning did not access credentials. Implementation verified native read-only queries through the existing `gh` login; Aide never extracts tokens.

**Setup:** install GitHub CLI and use its normal browser login (`gh auth login --hostname github.com --web`), reusing an existing suitable login where available. Aide checks tool availability and repository access, shows the host/account and actionable connection errors, and delegates read queries to `gh api` or `gh pr view --repo … --json …`. Login/repair remains an explicit user action rather than an interactive prompt in background polling. Missing `gh` or authorization disables GitHub monitoring without blocking workspace/runtime operations. Setup and verified versions are documented in the README; `just aide-doctor` checks the dependency.

**Organization approval:** GitHub CLI is a GitHub-owned privileged OAuth app. GitHub documents that these apps can be authorized even when an organization restricts ordinary OAuth apps. This removes the ordinary custom-Aide-OAuth-app approval step for the normal GitHub CLI login. It does not grant access beyond the user's permissions or remove SSO and other applicable access requirements; validate each target repository. This distinction was missing from the earlier authentication comparison. See [privileged OAuth apps](https://docs.github.com/en/apps/oauth-apps/using-oauth-apps/privileged-oauth-apps).

**Checks and permissions:** normal GitHub CLI OAuth login avoids the specific fine-grained PAT Checks API restriction. It can read private checks with the appropriate OAuth scope; Aide still needs to validate complete PR/check/review access. Aide issues only read queries, although the CLI credential may grant broader write permissions. Supplying a fine-grained PAT to `gh` does not upgrade that token's capabilities. Environment tokens such as `GH_TOKEN` and `GITHUB_TOKEN` take precedence over stored login, so connection diagnostics must distinguish credential sources without revealing their values. See [check-run authentication](https://docs.github.com/en/rest/checks/runs#list-check-runs-for-a-git-reference) and [CLI environment precedence](https://cli.github.com/manual/gh_help_environment).

**Storage:** let `gh` own credentials and their lifecycle. Its normal login uses the system credential store, with a documented plaintext fallback if that store is unavailable. Aide stores repository mappings, observations, and non-secret connection diagnostics only; no project token file, global token column, token copying, or custom Keychain integration is needed for this approach. Prefer authenticated CLI queries over extracting and caching `gh auth token`. See [CLI login](https://cli.github.com/manual/gh_auth_login) and [API queries](https://cli.github.com/manual/gh_api).

**Account selection:** a credential is not inherently tied to an Aide project. Proposed initial default is the CLI's active account for the explicitly selected host. Projects retain repository mappings and monitoring preferences. Do not change the user's active CLI account during polling. Multiple simultaneous accounts on the same host need a separate routing decision; do not promise independent per-project account selection merely because `gh auth switch` exists. Detect account/credential-source changes and refresh cached access/readiness. See [account switching](https://cli.github.com/manual/gh_auth_switch).

**Alternatives if needed:** direct fine-grained PATs allow selected-repository read permissions but require manual renewal, may need organization approval, and have a documented Checks API coverage gap. Classic PATs support check reads with broad scopes where permitted. A custom OAuth App offers a connection flow but broad repository scopes and potentially organization approval. A GitHub App supports narrow permissions but requires installation. These remain alternatives rather than additional first-version authentication methods. If Aide later owns credentials, the recommendation remains an OS credential store for secrets, global non-secret connection metadata, and project-local connection references. See [PAT limitations](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens) and [OAuth scopes](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps).

### Explicit PR association and responsibility

The user's workspace may move up and down commits or across a stack. Manually assign N PRs by URL or repository/number; persist each canonical identity until the user changes or removes that link. Treat links independently with stable display order and no stack metadata. Current Git branch or jj bookmark must not automatically retarget the task. A task without a PR, including an investigation, is normal. Linking does not check out commits or change workspace contents.

**Linking UX — implemented:** add a **GitHub PRs** section inside the expanded task, near its repository context. An empty section says **No linked PRs** and offers **Link PR**; unlinked tasks need no empty GitHub badge on the collapsed row. Link PR reveals an inline URL field with **Add** and **Cancel**. A full PR URL is the recommended initial input because it identifies host/repository/number without guessing; repository/number shorthand can follow where context is unambiguous. No modal or role selector is needed.

On Add (or Enter), show inline progress while resolving the PR and authenticated identity, then persist the link and display its title, repository/number, author, derived role, and current status. Fetch once immediately, then use the agreed background schedule. Retain input and show an inline error on invalid URL, missing login, inaccessible PR, or network failure so the user can retry. Keep draft input stable across dashboard snapshots. Duplicate addition identifies the existing link rather than adding another. Each linked PR gets its own collapsed-row tag; clicking the tag opens GitHub in a new tab independently of expanding the task. Arrange links outside the existing task-title button to preserve valid keyboard-accessible controls.

**Unlinking — agreed:** each PR entry in expanded details has an explicitly labelled **Unlink** action. It removes only that task's association, not the PR, branch, another task's link, or any GitHub state. Recompute task attention immediately without clearing other PR or harness reasons. Stop monitoring the PR only when no open task still links it. Unlinking is reversible by linking the URL again, so no confirmation modal is proposed. Keep the association visible if the operation fails, with a retryable inline error. Link/unlink operations are unavailable during task closing; completed task history remains read-only. Expose equivalent link/unlink operations through the CLI for terminal and task-agent use, sharing persistence and validation with the dashboard.

Optional branch/bookmark discovery can suggest candidates while linking. Suggestions must account for forks, detached Git HEAD, and jj bookmarks on a working-copy parent, without picking arbitrary repository bookmarks or trunk. Candidate discovery is a convenience, not a dependency for following a manually assigned PR. Preserve the link through rebases, reference deletion, PR merge, and task cleanup. Failed access means unavailable, not unlinked. The workspace's revision relationship to the PR is contextual information, not proof of an incorrect link.

**Responsibility — agreed:** determine the user's GitHub identity through the effective `gh` authentication for the PR's host. Use `gh api --hostname HOST user` (GET `/user`) or GraphQL `viewer` to obtain the handle and user ID. Compare the PR author's identity: same user means Implementing; another author means Reviewing. Display the handle, but prefer stable IDs within the same host for comparison so a renamed handle does not change ownership. No manual role selector or override is needed. Each link has its own derived role without imposing a single type on the task. Unknown identity/author yields unknown status, not an assumption that the PR belongs to somebody else. See [authenticated user API](https://docs.github.com/en/rest/users/users#get-the-authenticated-user).

Resolve identity at manager startup and connection repair, and validate it with polling batches (GraphQL `viewer` can be included in the same query). Use the same effective credential context for identity and PR observations, including environment overrides. On an account change, update the displayed account, invalidate old account-specific observations and review-request state, and recompute roles before publishing new actionable status. Cache identity per host/connection rather than making a separate identity call for every PR.

| Responsibility | What should stand out |
| --- | --- |
| Implementation / my PR | Summarize merge readiness: waiting for review, ready to merge, or needs attention because feedback/CI failures block merging. Underlying CI/review facts explain the result. |
| Review / someone else's PR | Review requested again implies review work; merged state signals the PR's outcome. Fetch request/outcome information only; omit CI and merge-readiness monitoring. |
| No linked PR / investigation | No GitHub action signal or requirement to add a PR. |

Review-request tracking uses the authenticated identity and GitHub's current requested-reviewer state. A direct outstanding request is actionable; a request after a prior submitted review can be labelled Review requested again. Persist enough observation/history to avoid inventing a new re-request on reload, but do not require a request transition to occur while Aide is running. GitHub removes a reviewer from the requested list when they submit a review; request removal/cancellation and merged/closed state also clear that action on the next poll. Read the user's own review history only as needed to distinguish re-requests. A request both made and answered between polls need not generate a historical alert: this feature tracks current work. Do not infer re-request from a new commit or unrelated comment. Team-request treatment remains to validate; do not equate every team request with an individual request without membership evidence. See [requested reviewers API](https://docs.github.com/en/rest/pulls/review-requests#get-all-requested-reviewers-for-a-pull-request). No GitHub inbox, notifications feed, or automatic intake of unrelated PRs is included.

### Per-PR tags and task attention — agreed direction

**Presentation:** render one compact tag for each PR next to the task ID, terminal, and Codex status. Include a PR identifier and text reason; do not rely on colour alone. Disambiguate identical PR numbers from different repositories. Link to the PR without toggling task details. Expanded details show per-PR role and freshness, with checks/feedback/blockers for own PRs and request/outcome information for review PRs, plus relevant local context. A few tags should fit naturally; let tags wrap on narrow screens without hiding terminal access. Exact icon/layout choices remain implementation details.

| Implementation PR condition | Display / action |
| --- | --- |
| Waiting for required review, with no actionable blocker | Grey: Waiting for review; idle, no attention |
| Ready to merge | Green: Ready to merge; actionable task reason is to merge |
| Feedback or CI failure blocks merge | Yellow: Needs attention, with a specific reason such as Changes requested / CI failed |
| Conflict or required branch update | Yellow: Needs attention, with the blocker |
| Checks queued/running or mergeability being calculated, without a known actionable blocker | Working/calculating label; no attention merely for waiting; working colour remains a presentation detail |
| Draft or waiting in a merge queue | Specific waiting label; do not infer an action solely from that state |
| Unavailable, stale, partial, or unknown data | Neutral: Unavailable / Stale / Unknown; do not claim ready or invent a CI failure |
| Merged or closed | Explicit terminal label; proposed purple for merged and grey for closed |

This supersedes the earlier red CI-failure tag and separate top-level feedback badge proposal. CI/review data still remain independent underlying observations, but the implementation PR's tag summarizes merge readiness and the user's next action. Review feedback is actionable when it blocks readiness (for example changes requested or required unresolved conversations), not merely because a historical or informational comment exists. No unread count, mark-as-read control, or persistent acknowledgment state is required. When blocking feedback is addressed and GitHub reports the updated state, the reason clears automatically; waiting for a fresh approval is grey if no actionable blocker remains.

Use GitHub's reported requirements and merge state, not just conflict-only `mergeable` or raw comment/check counts. A failed optional check can be shown in details without inventing a policy blocker when GitHub reports the PR ready. Absence of checks is not itself proof of readiness, but repositories with no required CI should not be blocked forever when readiness is otherwise known. Handle skipped, cancelled, pending, and failed checks explicitly. GitHub's [PR schema](https://docs.github.com/en/graphql/reference/pulls) exposes the underlying facts. For fresh observations, known actionable blockers outrank concurrent waiting/running states. Partial/stale responses cannot produce green. Remote CI describes the published PR, not unpushed local work.

**Review PRs:** a request/re-request addressed to the user is yellow and actionable. Otherwise the tag remains idle/waiting or shows Merged/Closed. Do not fetch or monitor CI, other reviewers' feedback, or merge readiness for review PRs. Merged is informational for both review and implementation links; the user decides when to close the task. Team-request policy and event detection remain implementation details to validate.

**Task aggregation:** any actionable PR makes its open task Requires attention, even if another linked PR is waiting or ready. Preserve all per-PR tags and identify actionable PRs in task reasons. Combine this with existing harness/runtime attention reasons; clearing one PR cannot clear another PR's or the harness's reason. Keep the native Codex status visible when it is working while GitHub requires attention. Count the task once in the existing browser-title attention total, regardless of how many PRs require action; task groups/counts remain mutually exclusive. Starting, closing and completed states retain precedence and do not acquire new GitHub attention.

**Agreed:** ready-to-merge implementation PRs contribute to Requires attention because merging is the user's next action, while retaining the green PR tag. Distinguish that reason from yellow blockers. Once all actionable GitHub reasons clear, fall back to the task's existing runtime-derived group; GitHub waiting must not suppress harness attention or mark a working agent idle. A temporarily failed refresh retains an already-known actionable reason as stale until refreshed, rather than implying the work was addressed; unknown access state alone does not invent PR work. Connection problems remain separately explained.

### Refresh, recovery, and validation

Use a manager-owned polling service and shared cache, separate from the two-second per-browser snapshot loop. Local reference inspection must avoid changing the workspace. Query explicit repository/PR identities, with timeouts and normalized errors, without blocking task operations. Poll while the manager runs, including with the browser closed; stopping Aide stops polling. On restart, present retained observations as cached/stale until refreshed. Browser reconnect reads the shared cache and schedules a refresh only when due; it does not start another poller. Multiple browser tabs and tasks sharing a PR share requests. Use role-specific field selections: implementation queries fetch CI/review/merge state; review queries fetch author/state and relevant review-request information without check/workflow calls or status rollups.

**Agreed refresh schedule:** on every manager startup, schedule a fresh fetch for every unique PR linked to an open task, regardless of cache age or previous next-poll time. This includes merged/closed links and gives restarting Aide the requested full-refresh behavior; retained observations are not a substitute for startup checks. Poll own PRs with queued/running CI about once a minute. Poll all other monitored PRs every five minutes, including review PRs, waiting/ready/blocked implementation PRs, mergeability still calculating without running CI, and merged/closed links on open tasks. Switch cadence when an observation changes the CI state. Completed tasks retain historical observations without polling. Fetch newly linked/relinked PRs and refresh affected PRs after connection repair; manual Refresh schedules an immediate fetch subject to rate-limit backoff. These are normal-operation targets, not latency guarantees. Local reference changes refresh workspace context without retargeting the linked PR or triggering redundant GitHub reads. Batch requests where useful, serialize per-host work, and apply a request budget across the planned 300-task maximum and the actual number of unique linked PRs, rather than assuming one PR per task. Respect rate-limit reset/retry headers and back off on failures; use conditional REST requests where supported. Freshness expires when the expected refresh window is missed; retain the last result and timestamp but show it as stale. Keep authentication, access, network, and rate-limit errors separate from CI failures. GitHub recommends webhooks where possible; local polling avoids adding an inbound hosting service to this feature. See [API polling guidance](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api).

Retain associations and last observations after cleanup, marked as historical; stop automatic polling completed tasks. Poll known merged/closed PRs more slowly while their task remains open so reopening can be detected. Cleanup never waits for GitHub availability and never becomes conditional on merge status.

## Milestone 1 — workspace lifecycle and attachable harness

## Project directory layout

A project has one root and N repositories. Each repository has a main checkout and a task-workspace folder. Operational bookkeeping lives in a dot folder at the project root, mostly in SQLite. Illustrative names:

```text
~/Projects/CatHerder/
  .aide/
    state.sqlite              # Project operational bookkeeping
  cat-herder/                  # Main repository checkout
  cat-herder-tasks/
    <task-id>/                # Dedicated task workspace
  another-repo/               # Optional related repository
  another-repo-tasks/
    <task-id>/
  settings/                   # Possible private preferences repo; not specified yet
```

Task IDs can be supplied at creation; later integrations may derive them from ticket or PR numbers. The project container leaves room for other files and independently version-controlled personal preferences. Do not introduce a settings schema or require a settings directory yet.

Operational state includes project/repository registration, task/workspace records, lifecycle progress, and eventual harness-session associations. Derive live facts from the filesystem, VCS, and harness where possible; these remain authoritative for their own state. The project database sits outside disposable workspaces. Exact schema, dot-folder/database names, and retention remain implementation decisions. Private project preferences may have a separate editable/version-controlled home; their format is not being specified yet.

**Global/project split:** keep a small SQLite database under `~/.aide` for registered project identities/paths and genuinely global operational state. Each project’s `.aide/state.sqlite` owns its repositories, tasks, workspace lifecycle, and harness-session associations. The dashboard aggregates those project databases; do not duplicate authoritative task records globally. Unavailable projects remain visible as unavailable. Global configuration, skills, and agent definitions remain editable files.

**Discovery:** the project’s `.aide/state.sqlite` is itself the marker; no separate marker file. Commands search ancestors for it and validate it as a project database. The global registry lets the dashboard find projects without scanning the disk. A project remains locally operable without its global registration, and can be re-registered after moving.

## Runtime revision — implemented

Use two managed windows in each task's peer tmux session: a work window containing fish and the native Codex UI, and a backend window containing the worker and dedicated Codex server. Exiting the UI must leave the backend and active work running. Tmux owns both windows; the worker handles recording and backend shutdown. Users can freely add windows for jj, local servers, and other work. Identify managed windows by stable tmux IDs/metadata, not their position or user-editable names; do not replace user-added windows during runtime recovery. Explicitly closing the whole task ends its whole session, including those windows. Reboot recovery restores managed windows, not arbitrary commands from user-added windows.

Recovery: retain the backend pane after its worker exits (`remain-on-exit`) so its output and stopped state remain visible. Stopping that worker stops its backend and interrupts active agent work, but does not complete the task. Attach/resume should check session/window identity and backend responsiveness, reuse healthy components, and repair missing or stopped managed components through the existing recovery path. Resume saved context idle and requiring attention; do not replay interrupted turns or run an immediate restart loop that fights a deliberate stop. Preserve user-added windows and never replace a pane running an unrelated command. Report failed repairs clearly and do not resurrect closing/completed tasks.

First-class control namespace: `aide codex resume`, replacing the shell-only `aide-resume` helper as the documented entry point. Use the current registered task tmux session as the task context, and open the native UI in the terminal where the command runs. This works from user-added windows and after changing directories. If the working directory belongs to a different task, report the mismatch rather than connecting silently. Outside a task session, direct the user to `aide task attach <id>` first; omit the proposed `--task` selector on resume. Do not infer the last-used task. Resume reconnects to a healthy backend without restarting it or submitting a turn, and works without the dashboard when the backend is alive. Missing-runtime recovery follows the existing manager policy. When resume recreates a stopped backend, use the invoking shell's exported environment, including variable removals, rather than the dashboard or tmux server's stale environment. Stopping the backend and then resuming is the environment-repair workflow; no separate restart command is needed. Additional harness namespaces can follow without implementing a general harness abstraction now.

Conversation association: after initial discovery of exactly one matching native conversation with saved history, bind its ID in the project database. That ID is authoritative for monitoring and resume; other conversations in the same directory cannot replace it. Ambiguous initial discovery requires attention. Untouched conversations without saved history remain unbound and can reopen fresh.

Codex 0.165 compatibility: initial discovery considers user conversations only. Loaded `thread_title` and other internal threads may share the workspace and client source but must not count as competing conversations. Use `threadSource` when available, with legacy subagent-source filtering for older servers. Successful observation/recording clears stale monitoring errors without clearing unrelated task errors. Verified with native metadata from two affected tasks, browser regression coverage for helper exclusion/error recovery and genuine ambiguity, and live dashboard checks after repairing their missing associations without restarting agents.

Recording efficiency: inspect native recording metadata at most every ten seconds and copy only changed files; flush pending changes on orderly backend shutdown and task cleanup. The cache is in memory, so a restarted worker may make one fresh copy. Native recordings remain the source of truth.

Concurrency: independent management commands run concurrently, including commands from one dashboard connection. Project-local task locks protect creation, recovery, attachment and cleanup across processes; conflicting task transitions report busy and can be retried. Repository mutations wait on a lock in Git’s common directory, shared by related checkouts. Short SQLite transactions protect read-modify-write updates; no project-wide lock spans a fetch or workspace deletion. Repository waits and deletion run on blocking workers. Startup recovery runs alongside the dashboard, and accepted operations continue if the browser disconnects. These locks coordinate Aide operations; jj/Git retain responsibility for external commands.

The root `README.md` now provides setup and usage instructions, a copyable first trial, tmux navigation, environment repair, recovery, review, and confirmed cleanup. It explains manager requirements and retained history/recordings.
